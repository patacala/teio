## graphify — Token Optimization Rules

This project has a knowledge graph at graphify-out/. Use it to AVOID reading files you won't edit.

### Core Principle
**If you're NOT going to Edit a file, do NOT Read it. Use graphify instead.**

### When to use graphify (ORIENTATION — replaces Read):
- Understanding what a module exports/does → `graphify explain "<module or concept>"`
- Finding how two things connect → `graphify path "<A>" "<B>"`
- Answering "what files are involved in X?" → `graphify query "<question>"`
- Starting a new task (orientation) → `graphify query "<task description>"` ONCE, then only Read files you'll edit

### When to use Read (EDITING — graphify can't replace this):
- You are about to write an Edit to that file (need exact current content)
- You need line-level precision for a bug fix
- graphify query returned insufficient detail for a specific file you'll modify

### Decision rule per file:
```
Will I Edit this file?
  YES → Read it
  NO  → Use graphify explain/query (saves ~500-1000 tokens per file)
```

### Commands:
- `graphify query "<question>"` — scoped subgraph answering a question (~200 tokens output)
- `graphify explain "<concept>"` — node details: exports, interfaces, relationships (~100 tokens)
- `graphify path "<A>" "<B>"` — connection chain between two nodes (~150 tokens)
- `graphify update .` — rebuild graph after code changes (AST-only, zero API cost)

### Additional:
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of source browsing
- Read graphify-out/GRAPH_REPORT.md only when query/path/explain don't surface enough
- Subagents: include "use graphify for orientation, only Read files to edit" in their prompts

## Documentation Rule

**NEVER create documentation files (README, .md, comments, JSDoc, etc.) unless the user explicitly requests it.**
- No auto-generated docs, no "helpful" READMEs, no summary files
- Do not add inline comments or docstrings to code you didn't write unless asked
- `graphify-out/` files are auto-generated by `graphify update .` — never manually edit them

## Code Comments Rule

**DO NOT write long comments explaining CSS/layout changes or design decisions.**
- Only comments when absolutely necessary for complex business logic
- No comments like "this change fixes X" or "we added Y for Z"
- No explanations of why a CSS class was removed or added
- Code should be self-explanatory
- If you need to explain design, do it in commit message, NOT in code
